## 版本、范围与当前证据

- 目标：`1.0.4` / `v1.0.4`，正式发布后 `prerelease=false`、Latest 指向该版本。
- 规划基线：master `09fd66a1b59aa405aebaebefb8afee3443b1c75b`，含已合入且五项 CI 通过的 PR #78。执行前重新 fetch，记录相对基线的新提交；不自动扩大冻结范围。
- 最新公开预发布：`1.0.4-dev.3`；稳定 Latest：`v1.0.3`。dev.3 三平台安装启动、双 Mac deep/strict 签名、14 附件及生产更新逻辑真实网络检查已有证据。
- 新增到正式候选：Beta Update 的双语 On/Off、勾号及统一左对齐。当前 Windows 本地 20 个语言/主题/切换/重启状态检查通过，未进入 dev.3 安装包。
- 正式版范围：H.264/JPEG 投屏与恢复、键盘/IME/粘贴、HAP 拖入和覆盖安装、商店失败回退、更新窗口与 Beta 通道、中英文界面，以及已有设备工具和本仓依赖源码维护。
- 不新增音频转发、手机到电脑剪贴板同步、息屏投屏或新的无线配对能力。离线真实图标、特定机型/受保护应用、无线调试及完整长期固件矩阵继续按 RUNBOOK 跟踪，不能改写为已完成。

## 全局约束与发布门槛

1. Windows 未签名是已接受的发行方式；macOS 两架构必须有效 ad-hoc、deep/strict 校验退出 0。公证、Gatekeeper 结果如实记录，不宣称具备 Developer ID 或消除系统警告，也不要求用户关闭全局安全策略。
2. 每个最终源码提交需独立审查和五项 CI 全成功；三个发行包必须来自同一确定 SHA，重新构建 1.0.4，不能给 dev.3 安装包改名后充当正式版。
3. 任一新增阻断问题、其他活动设备会话被误清理、安装后无法启动、更新指向错误版本/架构或附件摘要不一致，均暂停发布并回到修复验证。
4. 设备验收缺机器、固件或专用测试 HAP 时标记阻塞，不用 CI、mock 或历史版本结果替代。未覆盖固件在支持说明中明确列为未验证。
5. 保留 v1.0.3 和所有 dev tag/附件，不覆盖旧版本；应用 ID、配置目录和手动下载更新方式保持不变。
6. 公开前先完成所有可在草稿阶段进行的核验；公开后的真实更新检查另列结果，不把预置元数据测试写成在线发布验证。
7. 任务 4 所需的新验收驱动应在候选阶段准备。固定最终源码后仅补充证据；任何影响产物的代码、依赖、资源或打包变更都回到任务 1/3，重新审查、CI 和同源构建。

## 审查重点

- 旧版 1.0.3 与开发版升级路径不同：旧安装应用必须实际提示 1.0.4，不能仅用新 Provider 测试替代。
- Beta 关闭/开启都能看到较新的正式版；同版本不更新自身，网络失败可恢复，不降级。
- USB 重连、桌面异常退出及跨电脑接管不得破坏另一个活动客户端。
- 中文/英文和深浅色中菜单、成功提示与长文件路径可见；Beta 开/关文字必须和保存状态一致。
- macOS ad-hoc 完整性与系统信任是两项独立结果；发行附件和更新 YAML 必须覆盖正确架构。

## 建议排期与完成定义

设备、测试 HAP 和两台主机齐备且没有新缺陷时，建议安排 **1–2 个工作日**：先冻结与真机短测，晚上完成持续运行，随后最终包/升级验收及发布。CI 和下载等待可穿插文档整理；发现缺陷或缺少环境则按实际结果调整，不以排期压力跳过门槛。

正式版完成需要：固定源码与三平台同源包、发布前门槛通过、公开后更新检查通过、正式 Release/Latest 属性正确、附件下载核验完整、归档和已知限制同步。历史维护待办继续保持原状态。

推荐执行方式：由主代理顺序推进证据与发布步骤，在修复 PR 和最终发布门槛处独立复审；当前请求为规划，执行开始前由用户选择是否按此计划推进。
