# H.264 帧率与意外 JPEG 降级（2026-10-24）

## 结论与改动

当前设备的瓶颈在原生视频输出速率：应用基线接收 34.40 FPS、绘制 34.33 FPS，解码队列未积压。将原生服务 `-frameRate` 请求从 60 改为 120 后，同分辨率的实际应用接收和绘制均为 **60.12 FPS**。这只是请求目标，不代表实际输出 120 FPS；未改变手机系统刷新率、分辨率比例或桌面 GPU 策略，无 Java/JRE 和新依赖。

原先收到一次 `codec=error` 就将当前 ScreencastClient 永久切到 JPEG。现在每个客户端允许一次原生流重连，沿现有设备队列完成旧会话停止与新 generation 启动；再次流错误才切 JPEG。真正解码失败仍立即回退，配置包始终没有可绘制首帧的原有截止保留。过期 generation 的错误不能触发重连。主进程补充准备、候选库与流错误的原因日志。

## 测量与失败记录

脱敏计数见 [JSON](screencast-fps-tuning.json)，未保存屏幕内容或设备标识。

| 验证层 | 参数/场景 | 结果 |
| --- | --- | --- |
| 原应用，15 秒 | 请求 60、2412×1084 | 接收 516 帧，绘制 515 帧；34.40 / 34.33 FPS |
| 独立 NativeVideo，10 秒 | 请求 60、比例 1 | 33.29 FPS，仅编码流 |
| 独立 NativeVideo，10 秒 | 请求 120、比例 1 | 60.18 FPS，仅编码流 |
| 独立 NativeVideo，10 秒 | 请求 120、比例 0.5 | 60.06 FPS，无明显额外提升 |
| 新版实际应用，15 秒 | 请求 120、2412×1084 | 接收/绘制均 902 帧，60.12 FPS；错误/解码重启均 0 |
| 新版实际应用，连接中断 | 只销毁匹配视频转发端口的桌面 TCP socket | generation 1→2，2695 ms 后恢复绘制；788 个 H.264 事件、1 个预期错误事件，JPEG 0 |

新版应用绘制耗时 p50 3.2 ms、p95 3.7 ms；解码队列 p95 0、最大 1；绘制间隔 p95 31.1 ms、最大 59.1 ms。因此不能称完全匀速或没有偶发抖动。视频计数是输入包/Canvas 绘制次数，不是显示器实际呈现或画面独特内容帧数。前后不是相同内容逐帧重放；本轮观察带宽从约 8.96 增至 15.72 Mbps，不可据此断言所有内容的增幅。

独立探针最后一轮请求 60 时发生 `Native video stream ended`、0 帧。此时用户打开应用，应用实测已为 JPEG（3 秒 31 帧，约 10.3 FPS），renderer 记录了降级。探针与应用同时使用固定原生 socket，服务争用是最可能触发原因；旧版丢弃底层错误，无法追溯确认最初断流原因。该轮是失败记录，不能作为有效 A/B/A 对照。随后关闭/重开投屏恢复 H.264；后续测量只走实际应用，不再运行独立设备探针。

更新后一次启动探针等待 20 秒没有观测到画面；用户随后确认刚才动态内容已停止，并恢复播放。该次不计为成功启动，不将它武断归因为静止画面。后续成功打开观测为 H.264、约 1482 ms 首次 Canvas；本轮主要验收持续帧率与中断恢复，不作冷启动性能承诺。正常探测中 6.6-20260629 候选退出后选中兼容候选，不把该候选日志当作最终失败。

中断恢复使用实际应用已有的 HTTP/2 视频连接，未注入伪造帧或同时启动第二个手机服务。主进程记录了本次人为中断的明确错误，renderer 记录重试 H.264；返回画面后仍保持原分辨率。不是物理 USB 拔插测试。采样钩子、事件监听和临时 inspector 已移除，更新的开发应用保持投屏。

## 来源与验证范围

官方 HOScrcpy 参考源码 `cf6603b38586d457801ee93203e1a09a846b943e` 的 [API 文档](https://gitcode.com/OpenHarmonyToolkitsPlaza/HOScrcpy/blob/main/hoscrcpy%20API介绍.md) 记载帧率参数默认 120；只参考接口，桌面继续 Node HTTP/2，手机仍使用已固定哈希的原生候选库。帧率效果以本轮实测为准，不从文档推断所有设备表现。

- 定向应用回归 **80/80**：一次流错误重连、恢复 H.264 绘制、重复失败有界回退、过期错误隔离、解码不支持立即回退，以及捕获所有权、原生流/部署与解码边界。
- `npm run lint`、main/renderer 开发构建通过；实际 Electron 合成生命周期 **8/8**（与真机验证分开）。构建现存 Sass/eval/chunk 警告不等于运行失败。
- 本轮未重新跑全量应用测试、远端 CI、安装包或跨平台验收。长期功耗、固件矩阵、物理拔插及 M2 长期可靠性仍待验证，不能由当前约 60 FPS 推导全部完成。下一步优先做这些验收；源码与开发构建已更新，未提交或发布。
