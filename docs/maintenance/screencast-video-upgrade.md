# JPEG 回退后恢复视频

2026-10-25。用户反馈：静止打开投屏十余秒后回退 JPEG，随后恢复操作仍不会自动升回视频，希望自动尝试一次，并有手动入口，切换期间保持画面连续。

## 原因与实现

原路径只在 start 中尝试 H.264；首帧超时保留 JPEG 后没有恢复入口。重新调用 start 会停止现有捕获，因此不用于正常升档。

采用同一 capture lease 内的原地尝试：启动结算后收到内容不同的 JPEG 时，客户端自动尝试一次；工具栏的“切换到视频”允许手动尝试。相同静止帧不消耗自动机会，手动尝试也消费该窗口的自动机会，避免紧接着再次自动尝试。正在尝试时禁用重复点击；没有 VideoDecoder 时禁用入口。自动机会以客户端窗口生命周期计数，不随画质重启刷新。

JPEG 和输入在编码器启动期间保持可用；不增加 generation、不清空 Canvas、不停止 JPEG。新的视频帧附 promotion ID，客户端真正解码并绘制第一帧后才确认并停掉 JPEG。编码启动失败或启动成功后 5 秒仍未解码绘制，取消该次尝试并保留 JPEG。迟到视频帧通过 promotion ID、解码 epoch 和原会话 generation 丢弃。

主进程校验 sender、frame、session、generation 和 promotion 参数。队列只负责取得当前 lease，不把等待首帧放入设备输入队列；driver 保存待完成操作，关闭/换代时撤销路由并等待启动及清理完成，再释放设备。清理未确认时保留所有权。首帧交接已开始后发生断流/解码失败，仍走现有恢复路径，不能吞掉错误。

## 验证

- 定向自动测试覆盖自动尝试次数、手动重试、重复点击、静止帧不触发、JPEG 持续更新、输入不阻塞、实际绘制后确认、静默解码超时、旧帧和旧确认拒绝、关闭时失败/拒绝启动的串行清理，以及交接期间断流/解码错误恢复。
- 独立审查发现关闭时重复 native.stop、交接确认期间吞掉错误，以及初次 H.264 已有编码包但未解码时手动尝试会取消原恢复计时，已分别修复并加入回归；复审无 P1/P2。
- 真机入口：完整构建后退出其他投屏，保持一台已解锁手机静止，运行 `node script/check-static-screencast-start.cjs <报告.json> --upgrade`。第一轮保持静止，点击真实工具栏尝试视频，失败后保留 JPEG；第二轮日志出现 READY_FOR_MOTION 后手动连续滑动手机，记录 JPEG→H.264 首帧间隔。不保存屏幕像素或设备标识。
- 真机静止场景：第一轮手动尝试失败后仍保留 JPEG 和重试入口；第二轮收到用户滑动后的画面变化，promotion=1 自动切换并实际绘制视频。此轮最后 JPEG 到视频为 2952 ms，用户动作与画面间隔未严格控制，不据此判定持续运动期间的卡顿。
- 连续运动对照：增加 `--controlled-motion`，仅将初次 start 的 preferVideo 设为 false 建立真实 JPEG 基线，随后通过实际 Canvas 指针事件左右滑动桌面；采集、输入、视频尝试及解码均使用真实实现。自动交接记录 26 张 JPEG、647 帧 H.264，最后 JPEG 到首张视频 **14 ms**。加 `--manual-motion` 点击真实工具栏按钮后同样运动，记录 28 张 JPEG、644 帧 H.264，交接 **25 ms**。两轮 JPEG 都持续更新至首张视频。不是全程固件自然回退复现，也不保证所有设备具有相同延迟。
- 两次未满足静止 JPEG 基线的样本中，H.264 在测试阶段前已经输出，明确记为场景不成立，没有当作上述两项验收。最终原始统计及交接附近时间序列见[真机证据](screencast-video-upgrade-live.json)，不含屏幕像素或设备标识。
- 定向 74 项、完整应用 595/595、Licia 生产/fallback 两种模式各 606 passing / 4 pending、完整构建与 lint 通过；最终 CI 结果以本轮提交记录为准。测试程序只退出自己启动的进程；关闭会等待当前会话输入/视频清理。
