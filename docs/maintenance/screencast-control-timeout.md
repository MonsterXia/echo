# 投屏持续加载：UITest 控制超时与恢复修复

日期：2026-10-26（Asia/Shanghai）。状态：**本地修复及本机验证完成，跨固件/发布待验收**。基线 `4190f9a`，本地验收未替换安装包或发布；首轮修复构建与当时实机报告的 main asset SHA-256 一致；后续独立复审版本另列验证范围，见[脱敏统计](screencast-control-recovery.json)。

## 已确认的原因

USB 拔插前后发生设备变化及流中断，旧 UITest 控制服务/链路持续无响应；应用复用缓存 driver，旧 capture lease 的停止无法确认，后续启动反复停在同一路径。renderer 每次失败后继续重试，只有成功画面才能关闭加载状态，因此用户一直看到加载动画。

缓存连接重连与设备服务恢复是两个环节。旧实现会在 RPC 超时后销毁 TCP，下次请求重新握手，但缓存 driver 不执行新 driver 的初始化恢复；关闭再打开窗口也保留停止未确认的 lease。保留未知状态是必要保护，缺失的是受限恢复出口和可见错误状态。

最初为何无响应仍未确定：没有原故障进程的阻塞栈，不能区分 SDK 内部阻塞和转发链路异常，也不能声称已修复 SDK 死锁。

## 原始现场与诊断

- 已安装 Scrcpy Harmony 1.0.4-dev.0 的 app.asar 已包含 JPEG 启动预览和视频升档，不是缺少此前首帧修复的旧构建。
- 设备 nova 15 / PSN-AL00；param 返回 `OpenHarmony-7.0.0.105`，应用概览显示 `OpenHarmony 7.0.0.109`，保留来源差异，不推断固件变化。
- 用户日志 15:33 出现设备变化、原生流结束及停止未确认，15:45 后多次设备变化和 UITest 超时；日志没有日期，不据此推断故障持续时间。用户明确确认此前拔插过 USB。
- 故障现场 HDC 枚举/shell 正常、旧控制 daemon 与 TCP 8012 转发存在，没有本应用的原生扩展和视频 socket。真实 `Connection` 仅查询 getDisplaySize，3 秒超时，随后关闭探针连接。
- 正常退出并重启已安装应用后，控制 PID 更换、真实画面恢复，未重启手机。健康时相同直接查询为 16 ms；先 Driver.create 再查询为 5 ms，排除“该探针必然缺少握手”的解释。
- 修复前真实主进程/driver/会话模块加模拟设备传输：首次成功后 3 次重试及关闭重开共 4 次前台启动失败，reset 为 0，新捕获数仍为 1。显式初始化恢复后 reset 为 1、新捕获数为 2。
- 修复前真实 ScreencastClient 加模拟 IPC/时钟：30 秒内 7 次启动和错误，ready 未完成且仍有重试定时器。

旧 PID 的限定 hilog 没有内容，故障归档读取被拒绝；未提权。离线二进制观察到 session-death 在服务 mutex 内进入捕获停止回调，只有疑点，没有死锁证据。早期 JPEG 中断实验因已有原生捕获及随后设备离线而未执行；后续已完成的物理实验单独列于下文。

## 修复内容

1. **前台受限恢复。** `captureSessions` 在当前前台启动遇到明确控制传输失败时，最多尝试一次恢复。停止失败继续保留 lease；取消旧帧/输入路由，等待自己的原生流清理。`ControlRecovery` 核对预先记录的普通 daemon PID/starttime、其他原生捕获和 8012 活跃客户端，只终止仍匹配的一个控制进程；确认消失后清除旧私有回调，再握手及查询尺寸。恢复拒绝时保留未知状态，后台准备/普通输入/关窗不主动 reset，不重放未知结果输入，触摸释放义务仍保留。
2. **初始化与 SDK 检查保护。** 生产 CaptureUiDriver 永久禁用 UiDriver 广域停止，首次初始化和 SDK 更新也走上述受限路径。SDK 检查必须明确完成或确认文件缺失，空输出、HDC 错误不能当作缺 SDK 进而删除/上传；任何初始化失败关闭自身控制连接，避免未缓存连接遗留。
3. **有限重试及明确 UI。** 连续三次已结算启动失败或无首图后停止自动重试，显示错误和“重试投屏”。手动重试重新计数，实际画面绘制后进入 ready，组件销毁退订状态。
4. **可定位的错误。** 控制传输错误包含安全的 API 名称，例如 Captures.stopCaptureScreen、Driver.create，不记录输入参数或文本。

每条恢复清单/身份检查用 finiteShell 的 5 秒预算。初始 HDC shell、SDK 部署和转发仍采用既有传输，没有统一总截止；三次上限以每次启动 Promise 能结算为前提，不代表所有 HDC 挂起都已解决。

## 独立复审与二次修复（2026-10-26）

用户要求独立审视；新审查代理未继承实现过程，仅从当前源码、需求和差异复核。审查及补充失败用例确认并修复三项：

1. **P1：连接表部分读取失败仍允许恢复。** 原逻辑将 IPv4/IPv6 合并，只需一个表头；IPv6 拒绝读取时会忽略其中可能存在的其他客户端。现逐表核对命令完成标记、表头和每行地址/状态，未知或截断则拒绝终止。ps 清单同样需要完成标记，不能将截断列表当作旧进程已消失。新增四个失败回归先红后绿，另覆盖 IPv6 已连接和仅监听两种有效状态。
2. **P2：SDK 完成标记掩盖 I/O 错误。** 原 cat 管道后无条件输出完成标记。现由 grep 直接读文件，仅成功或确认无匹配时输出标记；执行/读取错误不更新 SDK。测试执行生产生成的真实 POSIX shell 命令，在读取边界注入错误，证明旧逻辑会误更新，新逻辑拒绝且无删除/上传。该 shell 用例在 Windows 跳过，跨平台通用解析回归仍运行。
3. **P2：预览出图绕过失败上限。** 启动尚未结算时 JPEG 预览就会清零次数，之后交接失败可反复循环且 UI 保持 ready。现在只有启动成功结算且已绘图才能清零；启动拒绝恢复 loading，连续三次预览后失败仍进入 failed 并停止自动重试。真实客户端回归先复现 ready/failed 断言失败，再验证修复。

二次全量应用测试 **620/620**、Licia 两模式各 **606 passing / 4 pending**、lint 通过；独立复审确认前述问题已修复，未发现新增明确阻断。新测试均使用隔离边界，不操作用户设备。二次修订完整构建通过，并已正常启动本地 dist；当前主窗口显示“未连接设备”。构建哈希及验证范围见最终验证数据。

复审时当前应用显示“未连接设备”，因此没有对二次修订版本重做真机拔插或持续超时实验；上文 553/5854 ms 是首轮修复版本的历史证据，不能当作二次修订版本的实测。

## 用户重新接入设备后的复验（2026-10-26）

使用二次复审后的同一构建（main SHA-256 `991d0aa0dd28eb6a604cff4e9fee49bf3ad7248178d032de5649868123fe548c`），本轮没有改生产源码或重复物理拔插。

第一轮正常 JPEG 出图，但控制故障恢复被另一个视频会话的 socket 占用保护拒绝，不能记为成功。随后确认桌面无应用实例、控制端口无活跃客户端，手机上仍有此前本应用生成的随机扩展进程及库（生成时间对应此前本地使用）。按已核对 PID/starttime 仅清理这一残留进程，确认退出及视频 socket 释放，未终止普通控制 daemon、未修改产品的跨会话保护。原失败报告与现场清理范围同时保留于脱敏数据。

第二轮实际 Electron/IPC/设备/Canvas 结果：

- 正常首图 **5932 ms**，JPEG，1206×542。
- 在测试应用内阻断 **4 次控制 RPC**，待生产恢复确认普通 daemon 已更换后解除阻断；同进程重开首图 **6019 ms**，随后有实际 H.264 绘制（2412×1084）。这是受控传输故障，不是 SDK 内部死锁复现。
- 使用真实 start handler 成功启动和预览后再注入 IPC 拒绝，累计 **3 次失败、3 次预览绘制**；真实界面显示失败状态，恢复原 handler 后点击“重试投屏”恢复画面。
- 测试正常退出，故障注入随测试进程结束，不进入交付应用。未保存屏幕像素。

新边界：应用退出/离线后遗留的视频扩展可能在后续进程中被视作其他会话，恢复因此被保守拒绝。本轮在现场确认后手动清理；产品尚无跨应用进程持久化所有权记录，不能宣称自动清理所有历史残留。后续若实现该能力，应记录并校验会话 token、设备和 PID/starttime，不能按名称前缀广域终止进程。

复验结束后正常启动同一 dist，点击投屏后确认 ready Canvas 与输入控件出现，保留窗口供用户使用；原安装包仍未覆盖。
