# 无缓存首次投屏的后台准备

日期：2026-10-24。用户要求提前探测兼容库和准备控制服务，缩短点击后的等待，继续不引入 Java。

## 行为和职责

`main/index.ts` 在 HDC 初始化后安装 `screencastPreparation.ts`。只对当前选中且 HDC 确认在线的设备准备；保存的旧设备选择不等于在线证据。选择/缩放来自现有 store，在线信息来自 HDC 列举和 tracker 的内部事件，无新增 renderer IPC。断连立即使准备任务失效，不等待主窗口延迟刷新。

`captureWarmup.ts` 管理选择代次和 **60 秒**保留期。每次选择/连接代次只准备一次，重复刷新、准备失败或 TTL 到期不会自动循环重启。准备成功后开始 TTL；切换、断连、过期及退出取消任务。过期释放原生扩展的进程、转发、临时库，控制服务和内存中的候选提示可供后续复用。

`captureSessions.ts` 把准备、正式启动、取消和清理放进同一设备队列。准备途中点击会等待同一任务，随后把资源所有权原子转移给正式 capture lease；过期回调不能停止已接管的投屏。清理失败保留不确定状态，后续启动必须先确认清理，不能绕开失败。准备前若其他工具占用视频 socket，不初始化或恢复控制服务。

`NativeVideo.prepare` 依次进行控制准备后的版本/ABI 查询、本地与远端完整性校验、候选上传、扩展加载和端口转发，**不调用 onStart、不取屏幕帧**。不能与控制初始化并发运行 `uitest --version`，前轮已证明会干扰 pidof。候选服务能监听后只保存内存提示；磁盘兼容提示仍等实际流握手成功才写入。点击后核对随机扩展名对应进程仍存在，再经已准备转发请求视频流；若进程已退出，先清理自己的资源再重新探测，不能误连接其他工具后来占用的 socket。请求尺寸变化则清理旧准备再按新尺寸启动。

退出先取消准备并等待设备队列清理，再允许 HDC 可选关闭。旧 `relaunch` 的 `app.exit()` 绕过生命周期，改为 `app.quit()`；主窗口在真正退出时不再因投屏可见而仅隐藏。退出也立即断开 renderer 帧路由，等待活动 capture lease 清理；失败记录为设备状态未确认，不伪造停止成功。

## 边界和复测

这是把约 5 秒的准备工作提前执行，并非把完全冷设备的全部工作压到 0.6 秒。刚连接就点击仍需等待尚未完成的准备；60 秒过期后需重新加载视频服务，但无需重复尝试已知不兼容的候选。仅当前固件真机实测；新手机控制 SDK 首次安装、其他固件、物理拔插和长期功耗仍待验证。断连/迟到任务用自动化回归覆盖，未进行物理拔插。HDC 控制初始化的 shell/文件传输尚无统一全链路截止，该既有边界仍适用于准备和退出等待。

分段复测：先关闭应用投屏和其他 UITest 工具，设置 `SCREENCAST_PROBE_CACHE` 为新的临时目录，执行 `node script/profile-screencast-start.cjs <report.json> --reset-control --prepare`。探针准备后等待约 2 秒采样 CPU ticks，再请求视频；与实际界面点击计时分开。实际应用自动预热可能占用 socket，探针会拒绝争用；需在应用准备过期/清理后再运行。

本轮当前设备目标完成，M2-2/M2-3 长期验收仍保持进行中；未提交、推送或发布。
