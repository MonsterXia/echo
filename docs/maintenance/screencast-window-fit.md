# 投屏窗口首帧比例适配

日期：2026-10-24。用户反馈默认显示框与手机屏幕比例不符，存在大片黑边，需要手动拖动。

后续：下文记录的 UITest 停止等待已有独立[定位与修复](screencast-first-frame-recovery.md)；本文件保留布局验收当时的状态。

根因：主进程只创建 500×640 或恢复保存的窗口宽高，未接收视频实际比例；renderer 仅用 Canvas 的 max-width/max-height 居中缩小。横屏 2412×1084 放入默认窗口时，视频高度约 225，而可用高度为 579，产生大面积上下留白。用户已经手动调到 1283×640 时测得画面高度 576.59、容器高度 579，印证问题来自窗口比例。

修复：首帧挂载后观察 Canvas 的 width/height 与容器尺寸，通过新增 `fitScreencast` IPC 报告视频尺寸和实测 UI 占用。主进程检查当前投屏主文档和有限尺寸，保留大致窗口面积、按画面比例计算宽高，计入原生窗口边框、标题栏、工具栏，并限制在当前显示器工作区。工具栏变为两行后重新计入高度。相同比例的后续帧、分辨率比例变化和普通手动缩放不反复重设窗口；最大化/全屏尊重用户状态。实际 Canvas CSS 尺寸按比例计算，低分辨率帧也能放大填满窗口，触摸继续按真实图像矩形换算。组件卸载会取消尺寸观察及迟到 ready 挂载。

验证：

- 新增主进程比例/旋转/工作区/发送者检查的三项回归在修复前失败，修复后通过；HTML 全屏暂缓适配回归亦先失败后通过。另覆盖相同比例缩放、手动调窗、工具栏换行、低分辨率放大及观察器释放。
- 全量应用 **507/507**、lint、main/preload/renderer 构建通过；真实 Electron 合成捕获生命周期 **8/8**。本轮未修改 Licia，未重复其上轮两套完整测试；没有重新制作安装包。
- 当前生产开发构建连接真实手机，将初始窗口设为 500×640，首帧自动适配为 **803×422**；画面 **803×360.875**，容器 **803×361**，水平留白 0、垂直剩余 **0.125 CSS 像素**。后续十秒计数与几何值见[脱敏 JSON](screencast-window-fit.json)，没有保存屏幕内容或设备标识。
- 真机重启期间曾卡在旧 UITest 连接的 `stopCaptureScreen` 回复等待：驱动对象已有连接、存在一个未结算请求、尚未进入 native capture。用已有驱动 stop 和应用 relaunch 后恢复。此恢复不等于修复该既有无截止等待，本轮不扩大窗口布局改动到传输生命周期。

状态：窗口比例修复及当前 Windows 真机首帧验收完成，已为用户重新打开应用和投屏。旋转、小工作区、全屏保护有回归覆盖，未进行物理旋转、多 DPI/跨显示器或 macOS 真机验收。下一步继续既有重连/停止请求长期可靠性与跨平台验收；未提交、推送或发布。
