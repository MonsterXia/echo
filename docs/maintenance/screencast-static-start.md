# 静止屏幕打开投屏迟迟无画面

日期：2026-10-25。来源为用户安装 1.0.4-dev.0 后导出的三轮启动日志，并在同一台亮屏、已解锁手机上复现。修复分支 `codex/fix-static-screencast-start`，基线 `14234fc`。

## 手机端证据与原因

设备固件为 `PSN-AL00 7.0.0.109(SP6C00E105R3P3)`。6.6-20260418 库在用户故障时段记录 `video encoder was successfully started`，但静止时桌面收不到首帧。随后尝试的 6.5/6.4 库记录 `set virtual screen surface failed`；部分其他候选在建立套接字前已经退出，退出的底层原因尚未确认。不能将这些不同失败都称为编码器初始化失败。

原逻辑把首帧沉默当成库不兼容，每个候选再等 5 秒，最终才启动 JPEG，造成数十秒空白。对照静止与有画面变化的实验支持“该固件的原生流依赖显示更新才能产出首帧”，但没有官方原生编码器源码，不能宣称已修复其内部实现。

重复帧参数改为库接受的 33、请求 IDR、单次 snapshot_display 均未可靠触发静止首帧，因此没有采用。测试中用户误触手机的样本不作为静止成功证据。现有 repeatInterval/bitRate 参数解析问题另行保留，不将未经验证的参数改动混入本次修复。

## 修复

- 控制服务就绪后先启动当前会话的实时 JPEG 采集；原生库准备与 H.264 首帧等待期间已有真实画面，原生成功后停止该 JPEG 采集。
- 原生启动必须收到非配置数据包；只有 SPS/PPS 不算成功。首帧 5 秒无输出时先发送有 2 秒截止的 onEnd，再确认本会话进程/转发/副本清理，继续已有 JPEG；不继续轮试全部库，也不删除已成功候选的兼容提示。真实部署/协议错误仍按原有兼容探测处理。
- JPEG 与原生采集分别保留清理状态，一个 stop 失败仍尝试另一个；未确认停止的 lease 继续保留。
- renderer 只在实际绘制 H.264 后阻止迟到 JPEG 覆盖。即使 JPEG 已显示，非配置视频到达但解码 5 秒仍无画面时仍会退回 JPEG，避免预览遮蔽原有恢复逻辑。独立审查发现该边界，已补红绿回归并复审。

## 验证与复测

应用回归 585/585；Licia 生产/fallback 两模式各 606 passing / 4 pending（原有外部夹具项）；lint、完整构建通过。无设备测试覆盖静止首帧的正常 onEnd、避免重复探库、配置包、预览交接、迟到 JPEG、解码无输出及双通道清理失败。独立复审无新增 P1/P2。

生产链路探针记录首张 JPEG 524 ms，原生选择结算 10430 ms。`firstFrameMs` 是实际收到首张非配置图片的耗时；`readyMs` 是整个 start 请求结算时间，不能再把它当作首帧时间。这次静止采样保持 JPEG，未声称 H.264 已出图。详见 [链路时序](screencast-static-profile.json)。

窗口验收使用 `node script/check-static-screencast-start.cjs <报告.json> [已安装程序路径]`：正常启动隔离配置，通过主进程 inspector 观察真实 preload/IPC、手机采集及 Canvas 绘制；只保存耗时、尺寸、帧数和编解码类型。初期浏览器自动化连接使此 Electron 环境的 VideoDecoder 不可用，那些样本只覆盖 JPEG，已排除出原生对照。最终探针要求真实 VideoDecoder 存在，不伪造视频帧。

三轮关闭及应用退出正常；退出后确认原生套接字和本次随机扩展进程均不存在，并删除诊断创建的手机端临时截图。没有保存手机画面内容。完全静止时 JPEG SDK 也可能只发送一帧，已撤回初版探针对“至少两帧”的错误假设；它不是卡死证据。上述结果说明本设备首图、实际视频交接及 JPEG 更新，不能外推持续帧率。

调试期间曾出现 `scrcpy-codec-cap.cjs` 的主进程错误弹窗：临时脚本错误地 require 了 Electron npm 包目录，拿到可执行路径而非运行时 API。已改正验证方式、结束该脚本进程并删除文件；不是应用源码异常，没有据此添加无关生产补丁。

当前修复不保证静止场景一定使用 H.264；保障的是及时显示真实画面并持续可用。新手机控制 SDK 首次安装、跨固件、长期运行、旋转及物理拔插仍待独立验收。没有修改或发布安装版；CI/交付状态见 RUNBOOK。
