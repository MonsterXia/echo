# 首帧等待与 UITest 连接恢复

日期：2026-10-24。用户要求继续修复窗口适配验收时出现的首帧等待挂起。

## 定位

当时运行态已确认：`startCaptureScreen` IPC 未结算，设备队列中存在后续等待，尚未建立 capture lease；UiDriver 有一个打开的 TCP 连接和一个未完成控制请求，`nativeActive=false`。请求停在启动前的 JPEG `stopCaptureScreen`，不是 H.264 解码或窗口比例计算。

源码存在三个确定缺陷：普通 `sendMessage` 默认 timeout 为 0；TCP end/error/close 没有拒绝未完成请求；主动 `end()` 只半关闭 socket，也不结束等待。因此失去一条回复就能永久占据设备串行队列。另外，请求 ID 由时钟和消息哈希产生，同一时刻的相同命令可能覆盖 Map 中的等待者；没有证据认定该碰撞造成了现场故障。

没有保存当时设备端协议日志，无法确认 SDK 为什么没有回复那条停止请求。本轮修复的是已确认的桌面无限等待及启动依赖，不把推断写成设备端根因。

## 修复

- 配有 nativeVideo 且没有尝试 JPEG 捕获时，不发送无关的 JPEG stop。JPEG start 发出前即记为“可能已启动”，只有真实 stop 成功才清除此状态；启动/停止失败仍阻止不安全的后续捕获。Native stop 的确认语义不变。
- 启动 native 前显式执行只读 `getDisplaySize`，准备 UITest 控制服务。原 stop 还承担了隐式初始化作用：第一版仅省略它，真机首次 16.852 秒后回退 JPEG，两次重开才成功。加入只读准备后重新验收，保留该失败轮次，不覆盖证据。
- 控制 RPC 默认 10 秒截止；JPEG stop 回复等待 3 秒；TCP 连接 3 秒，Driver.create 握手仍为 1 秒。超时、EOF、error、close、主动 end 共用终止路径，销毁 socket、拒绝全部未完成请求、清理计时器/缓冲区，并让 UiDriver 丢弃已关闭连接。后续调用重新建连和握手。
- 每条连接使用随机起点的递增请求 ID，避免同一时刻的相同请求覆盖等待者。成功回复清理计时器，连接/握手失败清理候选连接。
- 超时不等于设备停止成功；停止未确认时保留 capture lease。移除握手失败时自动杀 UITest/重发调用的旧分支，避免影响 native 扩展或重复结果未知的输入。正常初始化已有的 UITest 生命周期没有整体重构。

## 验证

- 四项本机真实 TCP 回归在修改前失败：EOF、主动关闭、单请求超时释放其他等待者、成功回复清理计时器。冷启动无关 stop 和控制通道准备断言也分别先失败后通过。
- 另覆盖默认截止、重复请求 ID、socket error、连接建立中取消，以及真实 UiDriver 静默 stop：约 3 秒拒绝并关闭连接，第二次 stop 经新 TCP/Driver.create 成功，未知结果 inputText 不自动重发。传输专项 **12/12**；会话层继续覆盖失败 JPEG start、停止未确认、迟到启动和 sender/generation 隔离。
- 最终应用全量 **517/517**；Licia 生产/fallback 各 **606 passing / 4 pending**；lint、主进程构建、真实 Electron 合成生命周期 **8/8** 通过。renderer/preload 沿用前轮通过的构建，本轮没有 IPC 接口变更。不将这些检查等同于完整 TypeScript、远端 CI 或安装包验收。
- 更新后的实际应用和真机：[脱敏计数](screencast-first-frame-recovery.json)。首次打开 **11007 ms**，关闭重开 **2388 ms / 2488 ms**，全部 **H.264、2412×1084**。UI 缩放至 0.5 后 **2905 ms** 收到 H.264 新尺寸 1206×542，恢复 1.0 后 **2990 ms** 收到 2412×1084。最后保持应用和投屏开启，恢复原比例，移除临时诊断。未保存屏幕内容或设备标识。

## 边界与下一步

本轮修复原生冷启动对冗余 JPEG stop 的依赖，以及 UITest 控制连接上的无限等待；首次约 11 秒仍含控制服务初始化和兼容库探测，不能宣传为秒开。丢失 stop 回复由本机 TCP 服务模拟；真机未强行丢弃回复，未做物理拔插。HDC shell/资源传输准备尚未全部纳入统一截止，不能声称整个启动链路已有一个总时限。设备若持续不回复停止，应用仍报告失败并保留停止未确认状态，不以超时伪造成功。

后续继续测量首次初始化/库探测分段耗时、物理断连及长期稳定性；M2-2/M2-3 其余验收不自动关闭。未提交、推送或发布。

后续初始化优化已完成当前设备验证：见[启动耗时记录](screencast-start-latency.md)。原 11 秒数据保留为历史基线；最终复用兼容提示及健康控制服务的应用重启首开约 2.33 秒。
