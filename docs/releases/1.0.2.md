# Scrcpy Harmony 1.0.2 发布清单

状态：发布准备中，未创建 `v1.0.2` tag 或 GitHub Release。版本接续上游 ECHO 1.0.1；本版本为 Scrcpy Harmony 首次独立发行。执行入口为 [RUNBOOK M0-2](../../RUNBOOK.md)。

## 可用于 Release 的说明

Scrcpy Harmony 是基于 liriliri/echo 独立维护的鸿蒙 HDC 桌面工具。本次更名并切换到独立的下载、反馈和更新源，保留上游作者署名、代码历史和 AGPL-3.0 许可证。

- 修复投屏图像尺寸与设备触控尺寸不同造成的点击偏移，明确投屏分辨率比例。
- 使用独立应用 ID `io.github.monsterxia.scrcpyharmony`，可与旧 ECHO 分开安装。**旧 ECHO 配置保留在原位置，不自动迁移**；首次启动需要重新配置应用设置。
- 固定 Electron 45，macOS 最低要求为 13。支持 Windows x64、macOS Apple Silicon（arm64）和 macOS Intel（x64）。
- 更新检查指向本仓库 Releases；发现更新后打开下载页面，由用户手动下载安装。

安装与验证限制必须随发行说明保留：CI 的安装和启动检查不代表真机兼容性验证。目标机型的触控、旋转、断连重连和长时间运行仍按 RUNBOOK 验收。Windows Authenticode、macOS Developer ID 签名、公证及联网下载后的 Gatekeeper 检查目前均未验收；不能将应用启动成功表述为系统安全验证通过。发布时如有新的验证证据，再更新这些状态。

## 执行与证据

1. 通过小范围 PR 合入版本与说明；等待该 PR 当前 head 对应的 `test`、`lint`、`windows-package`、`macos-package-arm64`、`macos-package-x64` 全部通过。
2. 在合入版本的提交上执行手动 Build。它上传三个 artifact，不创建 Release。记录运行 SHA；不要将不同提交或不同版本的 artifact 混用。
3. 下载并展开 artifact，按上表核对安装包和元数据。对**实际准备上传的安装包**再做安装启动验收并记录日志；PR CI 构建的包与 Build artifact 是不同构建，前者不自动证明后者已通过。
4. 逐项记录签名、公证和真机验证状态。Build 使用已有签名 secrets（若有），所以不能仅凭 CI 禁用签名就推断发布 artifact 的签名状态。校验 Windows 签名及 macOS `codesign`、公证/Gatekeeper 结果时保留命令和输出。
5. 核对发布源上的包版本、锁文件、CHANGELOG 与 `v1.0.2` 一致，将 tag 指向该源提交，再创建本仓库 Release，上传安装包、YAML、blockmap 及校验清单。填写实际发布日期并更新 RUNBOOK；在此之前维持“待发布”。
6. 发布后按 M0-3 使用两个明确版本的打包应用验证有更新、无更新及错误分支，记录平台、元数据文件和 Releases 跳转日志。
